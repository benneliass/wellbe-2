## Question

For the `delta` pill ("What changed?"), what are the delta semantics?
1. **What counts as a meaningful change** — new facts, status transitions, value deltas vs. baseline.
2. **Comparison window** — what time window is compared, and how is it chosen (fixed, since-last-visit, since-last-open)?
3. **Ordering/ranking** — how are deltas ordered for the user, calm and non-alarming, source-linked.

## Context

Touches C9 (Continuity & Closure Engine) and C4 (Processing) — see `docs/architecture/component-map.md`. Wrong delta semantics either hide real changes (a continuity failure — the thing WellBe exists to prevent) or manufacture noise/alarm (violating the calm, never-alarm guardrail).

# Track D Delta Semantics Research Brief

Prepared for Spike WEL-163. This brief is decision-neutral: it inventories external patterns and evidence relevant to a user-facing, source-linked, non-diagnostic "What Changed?" health view. It does not choose a final architecture, comparison window, ranking policy, or clinical threshold.

## External patterns to examine

### 1. Clinical event and status-change semantics

Health interoperability standards treat many health facts as timestamped resources with lifecycle states, not only as final values. HL7 FHIR defines `Observation` for measurements and subjective point-in-time assessments such as lab results, vital signs, device readings, and simple assertions ([HL7 FHIR Observation](https://fhir.hl7.org/fhir/observation.html)). FHIR `DiagnosticReport` provides context for diagnostic investigations and references the atomic `Observation` results that make up a report ([HL7 FHIR DiagnosticReport](https://fhir.hl7.org/fhir/diagnosticreport.html)). FHIR also distinguishes result lifecycle changes such as final, amended, corrected, cancelled, and entered-in-error states ([HL7 FHIR ObservationStatus](https://fhir.hl7.org/fhir/valueset-observation-status.html)).

For open loops, FHIR workflow resources model status transitions as first-class events. `Task.status` values cover states such as requested, received, accepted, rejected, in-progress, on-hold, failed, cancelled, and completed ([HL7 FHIR Task Status](https://fhir.hl7.org/fhir/codesystem-task-status.html)). The HL7 SDOH Clinical Care implementation guide states that `Task.status` communicates the status of referral fulfillment or patient-assigned to-dos and allows the initiator to understand whether the task is progressing ([HL7 SDOH Clinical Care - Checking Task Status](https://build.fhir.org/ig/HL7/fhir-sdoh-clinicalcare/en/checking_task_status.html)). FHIR `ServiceRequest` also describes a workflow in which the receiving organization accepts a request, updates it as work is performed, and finally issues a report referencing the fulfilled request ([HL7 FHIR ServiceRequest](https://fhir.hl7.org/fhir/servicerequest.html)).

Pattern to examine: treat "what changed" as a mixed stream of (a) newly available facts, (b) amended/corrected/withdrawn facts, (c) status transitions in open loops, and (d) numeric or categorical value changes. This pattern aligns most directly with C9 for pending/referral/result lifecycle and C4 for fact extraction and normalization.

### 2. Quantitative deltas: baseline, reference range, measurement noise, and biological variation

Laboratory medicine distinguishes a value outside a population reference interval from a meaningful change in an individual. MedlinePlus explains that lab reports use reference ranges, but normal varies by person and can be affected by age, sex, diet, medicines, and pre-test instructions; it also notes that clinicians may compare results to previous tests ([MedlinePlus - How to Understand Your Lab Results](https://medlineplus.gov/lab-tests/how-to-understand-your-lab-results/), [MedlinePlus - Laboratory Tests](https://medlineplus.gov/laboratorytests.html)). The ONC Interoperability Standards Platform notes that correct handling and interpretation of laboratory values requires the test instance, value, units, and reference range, with UCUM available for quantitative units ([ONC ISP - Representing Laboratory Result Values](https://isp.healthit.gov/representing-laboratory-result-values)). LOINC provides standard identifiers for health measurements, observations, and documents, supporting portability across systems, but LOINC identifiers do not by themselves supply local reference ranges ([LOINC](https://loinc.org/), [LOINC forum discussion on reference ranges](https://forum.loinc.org/t/standardized-reference-ranges-for-loinc-codes/2571)).

The laboratory delta-check literature uses reference change value (RCV) as a way to separate likely random variation from a meaningful individual change. CLSI EP33 describes delta checks for uses including detection of misidentified or compromised samples and clinically significant changes in patient results ([CLSI EP33 - Use of Delta Checks in the Medical Laboratory](https://clsi.org/shop/standards/ep33/)). A peer-reviewed review defines RCV as the minimum difference from a reference value considered distinguishable from measurement uncertainty and biological variation; it also states that biological variation and analytical imprecision are used to calculate RCV ([Application and optimization of reference change values for delta checks](https://pmc.ncbi.nlm.nih.gov/articles/PMC7755783/)). The EFLM Biological Variation Database describes within-subject and between-subject biological variation data as reference data for interpreting lab results and defining analytical performance specifications ([EFLM Biological Variation Database - Background](https://biologicalvariation.eu/background)).

Pattern to examine: numeric deltas can be classified by multiple external comparators: local reference range transition, change from prior value, change from personal baseline, RCV/biological-variation threshold, and condition- or measure-specific critical/significant-risk thresholds. These comparators are not interchangeable.

### 3. Patient-reported and symptom change: meaningful change is instrument- and patient-context-specific

Patient-reported outcome literature uses minimal important difference/change concepts to distinguish changes that are meaningful to patients from small score movements. FDA patient-focused drug development guidance emphasizes selecting, developing, modifying, and validating outcome assessments that measure outcomes important to patients ([FDA Patient-Focused Drug Development Guidance Series](https://www.fda.gov/drugs/development-approval-process-drugs/fda-patient-focused-drug-development-guidance-series-enhancing-incorporation-patients-voice-medical)). FDA's older PRO guidance describes the evaluation of patient-reported outcome instruments used to support labeling claims, including instrument validity and context of use ([FDA PRO Guidance](https://www.fda.gov/regulatory-information/search-fda-guidance-documents/patient-reported-outcome-measures-use-medical-product-development-support-labeling-claims)). PROMIS/HealthMeasures reports that, for group-level comparisons, a 2 to 6 PROMIS T-score point difference suggests meaningful change and that a 3-point threshold may be reasonable for many contexts, while acknowledging context dependence ([HealthMeasures - Meaningful Change for PROMIS](https://www.healthmeasures.net/score-and-interpret/interpret-scores/promis/meaningful-change)).

Pattern to examine: user-reported symptoms, function, pain, fatigue, and similar measures may require separate meaningful-change rules from labs, because the unit of meaning is often patient-perceived change or validated instrument score movement rather than lab analytical variation.

### 4. Provenance and source-linked claims

W3C PROV defines provenance as information about entities, activities, and people involved in producing a piece of data or thing, usable for assessing quality, reliability, or trustworthiness ([W3C PROV Overview](https://www.w3.org/TR/prov-overview/)). HL7 FHIR Provenance describes the activity that created, revised, deleted, or signed a resource and the involved entities and agents; FHIR notes that provenance can support assessments of quality, reliability, trustworthiness, and investigation of information origin ([HL7 FHIR Provenance](https://fhir.hl7.org/fhir/provenance.html)).

Patient-generated health data (PGHD) adds a provenance and quality dimension. The HL7 Personal Health Record Format IG defines PGHD as health-related data created, recorded, or gathered by patients or caregivers outside clinical settings, such as self-measured vitals and symptom diaries; it positions PGHD as complementary to EHR data between visits ([HL7 PHR Format IG - PGHD](https://build.fhir.org/ig/HL7/personal-health-record-format-ig/en/pghd.html)). ONC's PGHD project frames data infrastructure around capture, use, sharing, patient preferences, and barriers/opportunities for use in care delivery and research ([ONC PGHD project](https://aspe.hhs.gov/conceptualizing-data-infrastructure-capture-use-patient-generated-health-data)).

Pattern to examine: every displayed delta can carry a lineage bundle: original source, source type, capture/issued/effective timestamp, transformation activity, confidence/quality score, and links to the underlying raw or structured evidence.

### 5. Comparison-window patterns for "what changed since..."

External systems use several comparison windows:

- Fixed rolling windows. Apple Fitness/Health Trends compares the last 90 days of activity to the last 365 days and shows whether a metric is improving or declining ([Apple Support - Activity Summary and Trends](https://support.apple.com/guide/iphone/see-your-activity-summary-iph4c34a8a95/ios)). Fitbit Health Metrics lets users view trends and assess changes over time for metrics captured by Fitbit devices; related Fitbit/Google reporting has used 7-, 30-, and 90-day views for historical trend windows ([Fitbit Help - Health Metrics](https://support.google.com/fitbit/answer/14236917)).
- Encounter-anchored windows. After-visit summaries are encounter summaries meant to help patients understand and remember what happened during a visit and may include vitals, allergies, medications, orders, diagnoses, and upcoming appointments ([University of Iowa Health Care - After Visit Summary](https://epicsupport.sites.uiowa.edu/epic-resources/after-visit-summary-avs)). C-CDA provides templates for clinical notes and exchange documents, including structured clinical sections used across document types ([HL7 C-CDA IG](https://build.fhir.org/ig/HL7/CDA-ccda/), [HL7 C-CDA General Guidance](https://build.fhir.org/ig/HL7/CDA-ccda/generalguidance.html)).
- Last-seen or feed-style windows. Atom defines feeds as lists of entries with metadata for syndicated content ([IETF RFC 4287 - Atom Syndication Format](https://datatracker.ietf.org/doc/html/rfc4287)). W3C Activity Streams defines a JSON model for representing potential and completed activities and activity feeds ([W3C Activity Streams 2.0](https://www.w3.org/TR/activitystreams-core/), [W3C Activity Vocabulary](https://www.w3.org/TR/activitystreams-vocabulary/)).
- Event-anchored windows. FHIR Subscriptions establish proactive event notifications from a FHIR server to another system, with SubscriptionTopic defining concrete events such as resource interactions like create on Observation resources ([HL7 FHIR Subscriptions](https://fhir.hl7.org/fhir/subscriptions.html), [HL7 FHIR SubscriptionTopic](https://fhir.hl7.org/fhir/subscriptiontopic.html)).

Pattern to examine: comparison windows can be clock-anchored, encounter-anchored, user-attention-anchored, or event-anchored. The sources show all four patterns in use, but they serve different questions.

### 6. Calm ranking, notification, and digest presentation

General UX literature separates persistent state communication from interruptive notification. Nielsen Norman Group distinguishes indicators, validations, and notifications as different status-communication methods, with indicators used to make page elements stand out and notifications used to communicate events outside the user's current focus ([NN/g - Indicators, Validations, and Notifications](https://www.nngroup.com/articles/indicators-validations-notifications/)). Calm technology literature frames good systems as informing without constantly demanding attention; the Calm Tech Institute traces this to Weiser and Brown and lists principles around requiring the smallest possible amount of attention, amplifying the best of technology and humanity, and respecting social norms ([Calm Tech Institute - Principles](https://www.calmtech.institute/calm-tech-principles), [Weiser and Brown - Designing Calm Technology](https://people.csail.mit.edu/rudolph/Teaching/weiser.pdf)).

Health-specific evidence shows that patient access is valued but can create worry without context. ONC's Cures Act Final Rule supports access, exchange, and use of electronic health information and patient access to health data ([ONC Cures Act Final Rule](https://www.healthit.gov/regulations/cures-act-final-rule/)). A multisite JAMA Network Open study found that most patients supported immediate release of test results through portals, but some experienced increased worry, especially for abnormal results ([Perspectives of Patients About Immediate Access to Test Results](https://jamanetwork.com/journals/jamanetworkopen/fullarticle/2802672)). OpenNotes reports the same multisite finding: 96% of surveyed patients preferred immediate results, while increased worry was more common with non-normal results ([OpenNotes - Open Results](https://www.opennotes.org/open-results/)).

Alert-fatigue literature is relevant to ranking and suppression of low-value items. Clinical decision support studies describe alert fatigue as reduced responsiveness caused by excessive or irrelevant alerts ([Distinct components of alert fatigue in physicians' responses](https://pmc.ncbi.nlm.nih.gov/articles/PMC9748542/)). A mobile health push-notification study examined timing and frequency, reflecting the design risk that notification cadence itself affects use and burden ([The effect of timing and frequency of push notifications](https://pmc.ncbi.nlm.nih.gov/articles/PMC5207732/)). WHO's digital health guideline cautions that digital health interventions are not substitutes for functioning health systems and have limitations in what they can address ([WHO - Recommendations on Digital Interventions for Health System Strengthening](https://www.who.int/publications/i/item/9789241550505/)).

Pattern to examine: a "What Changed?" surface can be modeled as a calm digest/indicator rather than an urgent alert channel, while separately preserving explicit next-step handling for time-sensitive or critical-result workflows that already have clinical communication obligations.

## Decision-neutral findings

### Decision question 1: What counts as a meaningful change?

The sources support at least four externally grounded change categories. None of the sources collapses these categories into a single universal "meaningful" rule.

**A. Newly available facts or documents.** FHIR Observation and DiagnosticReport treat measurements and diagnostic reports as timestamped clinical resources, with DiagnosticReport providing context and references to atomic observations ([FHIR Observation](https://fhir.hl7.org/fhir/observation.html), [FHIR DiagnosticReport](https://fhir.hl7.org/fhir/diagnosticreport.html)). In WellBe terms, a new result, uploaded note, patient-entered symptom episode, device reading, or external document can count as a candidate delta because the record state has changed. C4 is the component most directly implicated in recognizing and normalizing these facts; C9 is implicated when the fact changes a tracked thread, result tracker, referral, or pending item.

**B. Corrections, amendments, withdrawals, and status changes.** FHIR ObservationStatus makes a distinction between final, amended, corrected, cancelled, and entered-in-error observations ([FHIR ObservationStatus](https://fhir.hl7.org/fhir/valueset-observation-status.html)). That means "changed" can include a change in trust or lifecycle state even if the user-facing numeric value is the same. For pending loops, FHIR Task and ServiceRequest sources treat lifecycle states as explicit data: requested, accepted, in-progress, on-hold, completed, failed, cancelled, and related states ([FHIR Task Status](https://fhir.hl7.org/fhir/codesystem-task-status.html), [FHIR ServiceRequest](https://fhir.hl7.org/fhir/servicerequest.html)). For C9, this maps directly to the pending-item ledger, referral lifecycle, result tracker, and post-visit plan checker. For C4, it means extracted facts need lifecycle metadata, not only labels and values.

**C. Value deltas against comparators.** Lab sources distinguish population reference ranges from individual change. Reference ranges describe expected values for a population or local lab, but MedlinePlus and ONC both indicate that interpretation depends on the specific test, units, reference range, and patient context ([MedlinePlus Lab Results](https://medlineplus.gov/lab-tests/how-to-understand-your-lab-results/), [ONC Lab Result Values](https://isp.healthit.gov/representing-laboratory-result-values)). LOINC can identify the kind of observation, but reference ranges are generally supplied by performing labs rather than by LOINC itself ([LOINC](https://loinc.org/), [LOINC reference-range discussion](https://forum.loinc.org/t/standardized-reference-ranges-for-loinc-codes/2571)). RCV literature adds another comparator: the amount of change likely to exceed analytical imprecision and within-person biological variation ([RCV delta-check review](https://pmc.ncbi.nlm.nih.gov/articles/PMC7755783/), [EFLM Biological Variation Database](https://biologicalvariation.eu/background)). For C4, this points to normalization of code, specimen/system, unit, reference range, method/source, timestamp, and baseline before a numeric delta can be treated as more than arithmetic difference.

**D. Patient-reported meaningful change.** FDA and PROMIS sources treat patient-reported measures as instruments requiring validation and context of use ([FDA PFDD Guidance Series](https://www.fda.gov/drugs/development-approval-process-drugs/fda-patient-focused-drug-development-guidance-series-enhancing-incorporation-patients-voice-medical), [FDA PRO Guidance](https://www.fda.gov/regulatory-information/search-fda-guidance-documents/patient-reported-outcome-measures-use-medical-product-development-support-labeling-claims)). PROMIS guidance gives a 2 to 6 T-score point range for group-level meaningful change and notes that a 3-point threshold may be reasonable for many contexts ([PROMIS Meaningful Change](https://www.healthmeasures.net/score-and-interpret/interpret-scores/promis/meaningful-change)). This supports a separate option space for symptoms and function: raw text changes, episode frequency, severity ratings, validated instrument score movements, and user-marked "this matters" events are different signal types.

**E. Critical or significant-risk result boundaries.** Critical-result sources define a separate patient-safety communication category. CLSI GP47 addresses policies for identifying, reporting, and managing critical/significant-risk laboratory results ([CLSI GP47](https://clsi.org/shop/standards/gp47/)). U.S. CLIA regulations require laboratories to immediately alert the requester or responsible user when results indicate imminently life-threatening or panic/alert values ([42 CFR 493.1291](https://www.ecfr.gov/current/title-42/chapter-IV/subchapter-G/part-493/subpart-K/subject-group-ECFR9482366886d579f/section-493.1291)). These sources do not define a general consumer digest ranking rule. They identify a boundary condition: some changes already belong to regulated clinical communication pathways rather than a calm summary alone.

**F. Source quality and provenance as part of meaning.** W3C PROV and FHIR Provenance define provenance as a basis for assessing quality, reliability, and trustworthiness ([W3C PROV](https://www.w3.org/TR/prov-overview/), [FHIR Provenance](https://fhir.hl7.org/fhir/provenance.html)). PGHD sources show that patient- and device-generated data can fill gaps between visits, but also bring source, context, and quality considerations ([HL7 PGHD](https://build.fhir.org/ig/HL7/personal-health-record-format-ig/en/pghd.html), [ONC PGHD project](https://aspe.hhs.gov/conceptualizing-data-infrastructure-capture-use-patient-generated-health-data)). For WellBe's source-linked constraint, a displayed delta is not only "a changed value"; it is a claim derived from one or more evidence sources with provenance and confidence.

### Decision question 2: What comparison window is used, and how is it chosen?

The sources show several established window families, each answering a different user question.

**Fixed rolling window.** Apple uses a 90-day recent window compared with a 365-day baseline for fitness trends ([Apple Trends](https://support.apple.com/guide/iphone/see-your-activity-summary-iph4c34a8a95/ios)). Fitbit Health Metrics presents device-detected metrics and trend assessment over time, with consumer reporting around 7-, 30-, and 90-day trend views ([Fitbit Health Metrics](https://support.google.com/fitbit/answer/14236917)). Fixed rolling windows smooth one-off noise and make recurring calculations simple. They can also be arbitrary relative to a specific health thread, lab cadence, menstrual cycle, medication change, or recent clinical event.

**Encounter-anchored window.** After-visit summaries focus on what happened during a visit and help patients remember discussion, orders, medications, and appointments ([After Visit Summary](https://epicsupport.sites.uiowa.edu/epic-resources/after-visit-summary-avs)). C-CDA provides clinical-document templates and structured sections for exchange ([C-CDA IG](https://build.fhir.org/ig/HL7/CDA-ccda/)). Encounter anchoring fits questions like "what changed since my last visit?" or "what is new after this appointment?" It can miss changes that happen between visits, across providers, or in patient-generated data not connected to an encounter.

**Last-seen or attention-anchored window.** Atom and Activity Streams provide general feed patterns in which entries/activities can be timestamped, ordered, and delivered as a list of changed content ([Atom RFC 4287](https://datatracker.ietf.org/doc/html/rfc4287), [Activity Streams 2.0](https://www.w3.org/TR/activitystreams-core/)). This supports a user-attention question: "what changed since I last looked?" It depends on reliably recording view state, read/unread state, and whether older-but-unseen items remain discoverable.

**Event-anchored window.** FHIR Subscriptions and SubscriptionTopic model proactive notifications for resource changes and concrete events such as resource create/update interactions ([FHIR Subscriptions](https://fhir.hl7.org/fhir/subscriptions.html), [FHIR SubscriptionTopic](https://fhir.hl7.org/fhir/subscriptiontopic.html)). Event anchoring fits questions like "what changed after a lab was issued?", "what changed after a referral was accepted?", or "what changed after the user added a symptom episode?" It depends on event quality, deduplication, and distinguishing event time from effective clinical time.

**Baseline window.** RCV and biological-variation literature imply that numeric deltas may need a baseline definition separate from the digest window. RCV is calculated from analytical and within-subject variation, and its comparator can be a prior value or selected reference value depending on method ([RCV delta-check review](https://pmc.ncbi.nlm.nih.gov/articles/PMC7755783/)). Apple-style rolling averages and lab RCV-style comparators answer different questions: one is trend direction over a fixed period; the other is whether a serial measurement change exceeds expected variation.

For WellBe components, C4 is implicated in the baseline comparator for value deltas, while C9 is implicated in the digest window for open-loop continuity events. The sources do not require these windows to be the same.

### Decision question 3: How are deltas ordered/ranked calmly, non-alarmingly, and source-linked?

The sources identify ranking dimensions but do not prescribe a single formula.

**A. Rankable dimensions from health standards.** FHIR and lab sources provide factual dimensions that can be used in ordering without inventing diagnoses: resource type, status transition, effective/issued time, source, correction/amendment state, reference range transition, result tracker state, task/referral state, and whether a result falls into a clinically managed critical/significant-risk workflow ([FHIR ObservationStatus](https://fhir.hl7.org/fhir/valueset-observation-status.html), [FHIR Task Status](https://fhir.hl7.org/fhir/codesystem-task-status.html), [CLSI GP47](https://clsi.org/shop/standards/gp47/)). RCV and PROMIS sources add measure-specific magnitude thresholds, but only where the measure and context support them ([RCV delta-check review](https://pmc.ncbi.nlm.nih.gov/articles/PMC7755783/), [PROMIS Meaningful Change](https://www.healthmeasures.net/score-and-interpret/interpret-scores/promis/meaningful-change)).

**B. Source-linked ordering.** W3C PROV and FHIR Provenance support attaching each derived delta to the data and transformation that produced it ([W3C PROV](https://www.w3.org/TR/prov-overview/), [FHIR Provenance](https://fhir.hl7.org/fhir/provenance.html)). For a source-linked health view, ranking can expose why an item appears: e.g., new source arrived, status changed, value crossed local range, value changed beyond chosen comparator, user marked a thread as important, or item is part of an unresolved pending loop. The sources support explainability of origin, not a single importance score.

**C. Calm digest versus interruptive notification.** NN/g distinguishes indicators from notifications, which is relevant to a home-screen pill: a persistent indicator can show that something changed without interrupting the user, while a notification is better suited to an event outside the user's current focus ([NN/g notification types](https://www.nngroup.com/articles/indicators-validations-notifications/)). Calm technology principles emphasize minimizing attention demand and moving information between periphery and focus as needed ([Calm Tech Principles](https://www.calmtech.institute/calm-tech-principles), [Designing Calm Technology](https://people.csail.mit.edu/rudolph/Teaching/weiser.pdf)). This supports an option space in which ranking can be visible, explainable, and non-sensational rather than optimized for urgency language.

**D. Anxiety and patient access.** ONC policy and patient-portal research show a tension: access is important, and most patients in the cited portal study preferred immediate release, but abnormal results were associated with increased worry for some users ([ONC Cures Act Final Rule](https://www.healthit.gov/regulations/cures-act-final-rule/), [JAMA Network Open immediate-results study](https://jamanetwork.com/journals/jamanetworkopen/fullarticle/2802672), [OpenNotes Open Results](https://www.opennotes.org/open-results/)). For a non-diagnostic product, this evidence is relevant to wording and ranking risks: ranking solely by abnormality, color, or worst-case interpretation can create anxiety; suppressing source-linked changes can reduce agency and continuity.

**E. Noise and alert fatigue.** Clinical decision support literature defines alert fatigue around excessive or irrelevant alerts and shows reduced responsiveness risks ([Alert fatigue study](https://pmc.ncbi.nlm.nih.gov/articles/PMC9748542/)). mHealth notification literature shows timing and frequency are design variables that affect app use ([Push notification timing/frequency study](https://pmc.ncbi.nlm.nih.gov/articles/PMC5207732/)). For a home digest, this supports treating low-confidence, duplicate, or tiny deltas differently from confirmed lifecycle changes or measure-specific meaningful changes. The evidence does not define exact suppression thresholds.

## Tradeoffs and open questions

### 1. Meaningful-change definition: broad event stream versus filtered semantic deltas

**Option space.** Maintainers can define a delta broadly as any new/updated source-linked fact or narrowly as only those changes that pass measure-specific, status-specific, or user-specific meaningfulness rules. FHIR event/status sources support broad inclusion; RCV, PROMIS, and critical-result sources support narrower domain-specific thresholds ([FHIR ObservationStatus](https://fhir.hl7.org/fhir/valueset-observation-status.html), [RCV delta-check review](https://pmc.ncbi.nlm.nih.gov/articles/PMC7755783/), [PROMIS Meaningful Change](https://www.healthmeasures.net/score-and-interpret/interpret-scores/promis/meaningful-change)).

**Risks of broad inclusion.** More noise, duplicate surfacing, and alert fatigue; more chance of turning routine administrative updates into anxiety-producing items. Alert-fatigue literature indicates that excessive or irrelevant alerts can reduce responsiveness ([alert fatigue study](https://pmc.ncbi.nlm.nih.gov/articles/PMC9748542/)).

**Risks of narrow filtering.** A continuity-relevant change can be hidden because no numeric threshold exists, because a status transition lacks a severity label, or because a user-specific concern is not captured by general clinical rules. PGHD and personal-context sources show that between-visit data may be meaningful even when not part of a clinical encounter ([HL7 PGHD](https://build.fhir.org/ig/HL7/personal-health-record-format-ig/en/pghd.html)).

**Open questions.** What minimum metadata must a candidate delta have before it can be shown? Are corrected/amended records always shown? Are duplicate source updates suppressed, grouped, or shown as provenance changes? Does a user-entered "this matters" marker override default thresholds?

### 2. Numeric delta threshold: reference range, prior value, RCV, personal baseline, or clinical threshold

**Option space.** Numeric change can be defined as (a) any value change, (b) crossing a local reference range, (c) percentage/absolute change from prior value, (d) exceeding RCV/biological variation, (e) crossing a clinician/lab critical threshold, or (f) change from a personal baseline. Sources make clear these are different constructs ([MedlinePlus Lab Results](https://medlineplus.gov/lab-tests/how-to-understand-your-lab-results/), [ONC Lab Result Values](https://isp.healthit.gov/representing-laboratory-result-values), [CLSI EP33](https://clsi.org/shop/standards/ep33/), [EFLM Biological Variation Database](https://biologicalvariation.eu/background)).

**Risks of reference-range-only semantics.** Lab reference ranges are local and population-oriented, and normal varies by person and context. A value can stay within range while changing meaningfully for an individual, or move just outside range without being clinically meaningful ([MedlinePlus Laboratory Tests](https://medlineplus.gov/laboratorytests.html), [LOINC reference-range discussion](https://forum.loinc.org/t/standardized-reference-ranges-for-loinc-codes/2571)).

**Risks of RCV-only semantics.** RCV depends on analyte-specific biological variation and analytical imprecision; coverage may be incomplete, and the concept comes from lab medicine and delta-checking rather than all personal health data ([RCV delta-check review](https://pmc.ncbi.nlm.nih.gov/articles/PMC7755783/), [EFLM Biological Variation Database](https://biologicalvariation.eu/background)).

**Risks of personal-baseline-only semantics.** Personal baselines require enough comparable history, stable units/methods, and context about source/device/lab. PGHD and consumer device data can be valuable but vary in source, quality, and context ([HL7 PGHD](https://build.fhir.org/ig/HL7/personal-health-record-format-ig/en/pghd.html), [ONC PGHD project](https://aspe.hhs.gov/conceptualizing-data-infrastructure-capture-use-patient-generated-health-data)).

**Open questions.** Should C4 compute multiple comparator labels for the same value? How are units, methods, specimen types, and lab-specific ranges normalized? What happens when the prior result comes from a different lab or device? Are trend deltas suppressed until enough history exists?

### 3. Comparison window: fixed, since visit, since last seen, event anchored, or layered

**Option space.** External patterns include fixed windows such as 90 days versus 365 days, consumer metric windows like 7/30/90 days, encounter summaries, activity-feed style last-seen windows, and event-driven subscription windows ([Apple Trends](https://support.apple.com/guide/iphone/see-your-activity-summary-iph4c34a8a95/ios), [Fitbit Health Metrics](https://support.google.com/fitbit/answer/14236917), [After Visit Summary](https://epicsupport.sites.uiowa.edu/epic-resources/after-visit-summary-avs), [Activity Streams](https://www.w3.org/TR/activitystreams-core/), [FHIR Subscriptions](https://fhir.hl7.org/fhir/subscriptions.html)).

**Risks of fixed rolling windows.** Easy to explain and stable against day-to-day noise, but arbitrary relative to a user's thread, test cadence, medication start, acute episode, or referral lifecycle. A fixed window can hide older unresolved changes or overemphasize recent low-importance items.

**Risks of since-last-visit windows.** Fits clinical continuity but can ignore user-generated data, specialist visits outside the source set, or changes that occur after a visit and before the next one. It also assumes that the visit is the relevant anchor for every Health Thread.

**Risks of since-last-opened windows.** Matches the user's attention state but can make salience depend on app usage habits. It requires reliable read-state tracking and a policy for important but previously unseen items.

**Risks of event-anchored windows.** Works well for result/referral/task events but depends on upstream event completeness, event deduplication, and clear semantics for event time versus clinically relevant time.

**Open questions.** Does the Home pill answer "since I last looked," "recently," "since my last visit," or "since this thread's anchor event"? Does each Health Thread carry its own comparison anchor? Are user-selected anchors allowed? How are older unresolved changes retained after the user has viewed the digest?

### 4. Ordering/ranking: recency, continuity risk, magnitude, confidence, source, or user priority

**Option space.** Deltas can be ordered by recency, source confidence, lifecycle status, open-loop state, result issuance time, magnitude relative to chosen comparator, user-marked importance, or source type. Standards provide fields and provenance for these dimensions but not the final score ([FHIR Provenance](https://fhir.hl7.org/fhir/provenance.html), [W3C PROV](https://www.w3.org/TR/prov-overview/), [FHIR Task Status](https://fhir.hl7.org/fhir/codesystem-task-status.html)).

**Risks of recency-first.** Recent minor updates can bury unresolved pending items or significant corrections.

**Risks of magnitude-first.** Numeric size can be misleading across analytes and instruments. Meaningful change depends on units, reference range, analytical imprecision, biological variation, and patient context ([ONC Lab Result Values](https://isp.healthit.gov/representing-laboratory-result-values), [RCV delta-check review](https://pmc.ncbi.nlm.nih.gov/articles/PMC7755783/)).

**Risks of abnormality-first.** Portal evidence indicates that abnormal results can increase worry for some users, even though most users prefer timely access ([JAMA immediate-results study](https://jamanetwork.com/journals/jamanetworkopen/fullarticle/2802672), [OpenNotes Open Results](https://www.opennotes.org/open-results/)). Abnormality-first ranking may also imply diagnosis or urgency where the product identity is explicitly non-diagnostic.

**Risks of user-priority-first.** Personal relevance aligns with user agency, but a user may not know which clinical follow-up loops are open or time-sensitive. WHO cautions that digital health is not a substitute for functioning health systems ([WHO Digital Health Guideline](https://www.who.int/publications/i/item/9789241550505/)).

**Open questions.** What ranking factors are permitted to imply salience without implying diagnosis? Is there a separate bucket for "open loops changed" versus "values changed" versus "sources corrected"? Does each item disclose the ranking reason in plain language? Are urgent/critical-source categories handled outside the calm digest or inside it with bounded language and next steps?

### 5. Calm presentation: digest/indicator versus alert channel

**Option space.** The Home pill can behave as a persistent indicator, a digest entry point, an unread-count surface, or an interruptive notification. NN/g's distinction between indicators and notifications and calm-tech principles provide a design vocabulary for this choice ([NN/g notification types](https://www.nngroup.com/articles/indicators-validations-notifications/), [Calm Tech Principles](https://www.calmtech.institute/calm-tech-principles)).

**Risks of too-calm presentation.** A meaningful continuity change may be under-noticed, especially if it relates to a pending test, referral, or corrected result.

**Risks of too-alerting presentation.** The product can manufacture anxiety, invite overchecking, or contribute to notification fatigue. Patient-portal and mHealth evidence both show worry/frequency considerations ([JAMA immediate-results study](https://jamanetwork.com/journals/jamanetworkopen/fullarticle/2802672), [push-notification timing/frequency study](https://pmc.ncbi.nlm.nih.gov/articles/PMC5207732/)).

**Open questions.** What language is allowed for an item whose source labels it high, low, abnormal, corrected, or critical? Does each delta require a next step, a source link, or both? Are counts shown only after deduplication/grouping? Does the surface say "changed" rather than "worse" unless a source explicitly supports that wording?

### 6. Source-linked transparency: derived claims versus raw evidence

**Option space.** A delta can show only the summary, summary plus source labels, or a full provenance trail. PROV and FHIR Provenance support source and transformation traceability ([W3C PROV](https://www.w3.org/TR/prov-overview/), [FHIR Provenance](https://fhir.hl7.org/fhir/provenance.html)).

**Risks of summary-only.** Orphaned claims can violate the source-linked principle and make it hard for users to correct or contextualize a delta.

**Risks of full provenance everywhere.** Too much metadata can overwhelm a calm view and obscure the plain-language point.

**Open questions.** What is the minimum visible source cue per item? What provenance detail is one tap away? How are conflicts between sources displayed? When C4 confidence is low, is the item suppressed, grouped under "needs review," or shown with uncertainty language?

### 7. Corrections and user control

**Option space.** Corrected/amended/entered-in-error upstream records can be treated as first-class deltas, grouped with their original item, or shown only inside source history. FHIR explicitly models corrected/amended/entered-in-error states ([FHIR ObservationStatus](https://fhir.hl7.org/fhir/valueset-observation-status.html)).

**Risks of hiding corrections.** The user may retain an outdated understanding of a result or status.

**Risks of overemphasizing corrections.** Some corrections may be technical, duplicate, or non-substantive; surfacing every correction can create noise.

**Open questions.** What kinds of corrections are always visible? Can the user dismiss a delta without deleting the source-linked evidence? How does a user correction to their own memory interact with upstream clinical records and C4-derived facts?

## Approaches considered

Grounded only in the recorded research:

- **What counts as change.** The research distinguishes four externally-grounded categories that no source collapses into one rule: (A) newly available facts/documents (FHIR Observation/DiagnosticReport), (B) lifecycle/status changes (FHIR ObservationStatus amended/corrected/withdrawn; Task/ServiceRequest pending/referral/result transitions), (C) value deltas against *different* comparators (reference-range crossing vs. change-from-prior vs. personal baseline vs. RCV/biological-variation), and (D) patient-reported meaningful change (PROMIS-style instrument movement, episode frequency, user-marked "this matters"). A fifth boundary category (E) — critical/significant-risk results (CLSI GP47, CLIA 42 CFR 493.1291) — already belongs to regulated clinical communication pathways.
- **Comparison window.** Four window families each answer a different question: fixed rolling (Apple 90/365, Fitbit 7/30/90), encounter-anchored (after-visit summary, C-CDA), last-seen/attention-anchored (Atom, Activity Streams), and event-anchored (FHIR Subscriptions). The numeric *baseline* comparator is separate from the digest window.
- **Ranking.** Standards supply rankable dimensions (resource type, status transition, effective/issued time, source, correction state, range transition, open-loop state) and provenance for explainability (W3C PROV, FHIR Provenance), but no single importance score. NN/g and calm-tech separate persistent *indicators* from interruptive *notifications*; portal/OpenNotes evidence shows abnormality-first ranking can manufacture worry; alert-fatigue evidence warns against surfacing low-confidence/duplicate/tiny deltas.

## Decision

1. **Meaningful change = a typed, source-linked change-event stream.** C4 emits change-events tagged with category — (A) new fact/document, (B) lifecycle/status change, (C) value delta with *multiple comparator labels* (range-crossing, change-from-prior, personal-baseline, and RCV only where biological-variation data exist), (D) patient-reported change — each carrying lifecycle metadata, confidence, and a provenance link. Critical/significant-risk results (E) are detected but handed to the existing continuity next-step flow (C9), not dramatized in the calm digest.
2. **Comparison window = layered and anchor-aware.** The Home `delta` pill defaults to *"since you last looked"* (attention-anchored, requires per-user read-state). Each Health Thread additionally carries its own anchor: event-anchored for result/referral/result-tracker lifecycle (C9), encounter-anchored where a visit exists. Numeric value deltas use a **separate baseline comparator** (prior value / personal baseline) independent of the digest window. Older unresolved changes are retained after viewing, never dropped.
3. **Ranking = calm, explainable, source-linked — never abnormality-first.** Order: open-loop continuity changes (C9) → lifecycle corrections → comparator-crossing value changes → new facts → patient-reported. Every item states its ranking reason in plain language ("status changed", "new result", "changed vs. your baseline") and shows at least one source cue (provenance one tap away). Copy says *"changed,"* not *"worse,"* unless a source explicitly supports it. Low-confidence, duplicate, or tiny deltas are grouped/suppressed by C4 confidence rather than shown as separate items. The pill is a persistent **indicator/digest**, never an interruptive alarm channel.

## Trade-offs accepted

- **Inclusive (source-linked) change stream with confidence-based grouping** over narrow threshold-only filtering: accepts some noise risk to avoid hiding continuity-relevant changes — the failure mode WellBe exists to prevent — mitigated by grouping/suppression and mandatory ranking reasons.
- **Per-thread anchors + separate value baseline** add computation/complexity vs. a single fixed window, accepted because a fixed window is arbitrary relative to a thread, lab cadence, or referral lifecycle.
- **Multiple comparator labels per value** add C4 cost; we will **not** invent RCV where analyte biological-variation data are absent and instead fall back to range/prior-value labels.

## Implementation notes

- **C4:** emit change-events with `category`, lifecycle metadata, comparator labels + values, `confidence`, and `sourceRef`; compute per-user read-state for "since last looked".
- **C9:** owns open-loop/result-tracker/referral lifecycle transitions that feed the digest and routes critical-result category to the pending-item/next-step flow.
- Each rendered item carries `rankingReason` + `sourceRef`; counts shown only after dedup/grouping; wording defaults to "changed".
- **Deferred (tracked, not blocking):** exact suppression thresholds, personal-baseline sufficiency rules, and final copy — to implementation tuning with user research.
