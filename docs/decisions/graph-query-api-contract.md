## Question

For the `graph` pill ("Open the graph"), what is the thread-scoped graph read/query API contract over the existing C6 schema?
1. **Query shape** — thread-scoped node/edge selection, traversal depth, edge-type filters.
2. **Response contract** (C13) — the shape a viz client consumes.
3. **Viz scoping** — what subset renders (Cytoscape thread view per WEL-78), and how unscoped data is kept out.

The C6 schema itself is already decided (WEL-98, WEL-135, Done); this spike is about the **read/query contract**, not a schema change.

## Context

Touches C6 (Knowledge Graph, read consumer) and needs a C13 endpoint — see `docs/architecture/component-map.md` and `docs/system-design/knowledge_graph.md`. A wrong query contract either leaks unscoped data (privacy) or forces a breaking API change later.

# Track F: Thread-scoped graph read/query API contract for a visualization client

This brief is decision-neutral. It treats WellBe's product guardrails as fixed constraints: personal-first and user-controlled access, strict per-user and per-thread scoping, source-linked evidence, and non-diagnostic graph semantics where `may_explain` is the strongest causal edge type exposed by the product.

## External patterns to examine

### 1. Graph-query-over-HTTP endpoints

Established graph platforms commonly expose graph read operations over HTTP while keeping traversal semantics in a graph query language. Neo4j's current Query API executes Cypher statements over HTTP and is positioned for applications that need HTTP access rather than a supported driver; Neo4j also notes that this Query API supersedes its earlier HTTP API pattern ([Neo4j Query API](https://www.neo4j.com/docs/query-api/current/)). Amazon Neptune exposes an openCypher HTTP endpoint that accepts read and update queries through HTTP GET and POST, with examples such as `MATCH (n1) RETURN n1` ([Amazon Neptune openCypher HTTPS endpoint](https://docs.aws.amazon.com/neptune/latest/userguide/access-graph-opencypher-queries.html)). Apache TinkerPop's Gremlin documentation frames Gremlin as a graph traversal language intended to work across graph providers, while noting that provider capabilities and limitations vary ([Apache TinkerPop Gremlin Reference](https://tinkerpop.apache.org/docs/current/reference/)).

For Track F, this pattern is relevant to C13 because a REST/OpenAPI boundary can either expose a typed graph-read operation or act as a constrained gateway to a graph query language. It is relevant to C6 because any graph-query-over-HTTP shape still needs server-side anchoring to the authenticated user and requested thread rather than trusting client-supplied graph reachability.

### 2. Bounded traversal, hop limits, filters, and result cost controls

Cypher supports variable-length graph patterns for matching paths of bounded or unbounded length, including patterns that find nodes reachable from an anchor or paths connecting nodes; the Cypher manual describes quantified path patterns and quantified relationships as mechanisms for graph patterns of unknown length within a range ([Neo4j Cypher variable-length paths](https://neo4j.com/docs/cypher-manual/current/patterns/variable-length-paths/)). GraphQL security guidance, while not graph-store-specific, documents analogous controls for nested relationship traversal: paginated fields, depth limiting, breadth limiting, query complexity analysis, and rate limiting to constrain deeply nested or cyclic requests ([GraphQL Security](https://graphql.org/learn/security/); [GraphQL.js Operation Complexity Controls](https://www.graphql-js.org/docs/operation-complexity-controls/); [OWASP GraphQL Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/GraphQL_Cheat_Sheet.html)).

For Track F, these sources identify common external controls to examine for a graph read contract: maximum traversal depth, allowed relationship or edge types, allowed node types, maximum nodes and edges, maximum page size, complexity or cost limits, and timeout behavior. They do not define a WellBe-specific traversal policy; they establish that relationship traversal must be bounded and that the server should enforce those bounds.

### 3. Pagination and cursor/page-token patterns

Pagination is treated as part of an API contract rather than an implementation detail in several established API design sources. Google AIP-158 states that responses from list-like operations can grow arbitrarily and that adding pagination later can be backward-incompatible, so pagination should be included from the start when needed ([Google AIP-158: Pagination](https://google.aip.dev/158)). AIP-158 uses `page_size`, `page_token`, and `next_page_token`, and requires that all other request parameters match when a page token is used ([Google AIP-158: Pagination](https://google.aip.dev/158)). GraphQL's pagination guidance and the Relay Cursor Connections specification use a connection model where edges carry cursors and nodes, and a `pageInfo` object tells clients whether additional pages exist ([GraphQL Pagination](https://graphql.org/learn/pagination/); [Relay Cursor Connections Specification](https://relay.dev/graphql/connections.htm)).

For Track F, these patterns are relevant because a per-thread subgraph may still be large. Pagination choices can apply to nodes, edges, paths, adjacency expansion frontier, or complete graph chunks. The sources establish cursor/page-token and connection-style patterns, but they do not settle which graph-specific unit should be paginated.

### 4. Filtering patterns for list-like and relationship-like reads

Google AIP-160 treats filtering as a field that evolves more often than most request fields, and standardizes on a single string `filter` field with a structured grammar for equality, ordering, logical operators, and related-object traversal or functions ([Google AIP-160: Filtering](https://google.aip.dev/160)). GraphQL exposes relationship fields that can be filtered and paginated as part of the schema; the connection model also creates an edge layer where edge-specific data can travel alongside each node ([GraphQL Pagination](https://graphql.org/learn/pagination/); [Relay Cursor Connections Specification](https://relay.dev/graphql/connections.htm)).

For Track F, external filtering patterns to examine include typed arrays such as `nodeTypes` and `edgeTypes`, a structured filter string, or schema-defined filter arguments. The evidence shows that filters must be considered evolvable contract surface and that edge-specific metadata is a recognized response concept.

### 5. Node-link response formats for visualization clients

Cytoscape.js accepts element JSON where nodes and edges carry a `data` object; node IDs are mandatory, and edges are inferred by `source` and `target` values inside edge data. Cytoscape accepts either a flat elements array or `elements: { nodes: [...], edges: [...] }`, and its `cy.json()` import/export mechanism uses the same JSON format as initialization ([Cytoscape.js JSON format](https://js.cytoscape.org/)). Sigma.js uses Graphology as its underlying graph model, and Sigma documents node attributes such as `x`, `y`, `type`, `size`, `color`, and `label`, plus edge attributes such as `size`, `color`, `label`, and `type` ([Sigma.js graph data](https://www.sigmajs.org/docs/advanced/data/)). Graphology serialization represents nodes with `key` and optional `attributes`, edges with `source`, `target`, optional `attributes`, and optional edge `key`, and whole graphs with `attributes`, `options`, `nodes`, and `edges` ([Graphology serialization](https://graphology.github.io/serialization.html)).

For Track F, these formats define concrete visualization-consumer shapes to examine: Cytoscape-native elements, Graphology/Sigma-native serialization, or a neutral node-link format transformed client-side or server-side.

### 6. Neutral graph serialization and metadata containers

JSON Graph Format describes a JSON structure for graph data with node and edge metadata fields, uses meaningful graph property names, and provides a JSON Schema for validation ([JSON Graph Format](https://jsongraphformat.info/); [JSON Graph Format specification](https://github.com/jsongraph/json-graph-specification/blob/master/README.md)). The JGF edge structure includes `source`, `target`, optional `relation`, optional `directed`, and optional metadata; graph, node, and edge objects can carry metadata ([JSON Graph Format specification](https://github.com/jsongraph/json-graph-specification/blob/master/README.md)).

For Track F, this pattern is relevant to C13 as a canonical or adapter-friendly response option. It is not specifically a Cytoscape or Sigma native shape, so a visualization client may need conversion if the API returns JGF directly.

### 7. Provenance and evidence metadata patterns

W3C PROV-O defines a vocabulary for representing and interchanging provenance information across systems and contexts, and it is designed to be specialized for domain-specific applications ([W3C PROV-O](https://www.w3.org/TR/prov-o/)). W3C PROV-DM defines provenance around entities, activities, derivations, agents, and bundles with extensibility points for domain-specific use ([W3C PROV-DM](https://www.w3.org/TR/prov-dm/)). PROV-JSON is a JSON representation of PROV-DM designed for client-side manipulation and web-service interchange ([W3C PROV-JSON](https://www.w3.org/submissions/prov-json/)). HL7 FHIR Provenance tracks activities that created, revised, deleted, or signed resource versions, and describes the entities and agents involved so that consumers can assess quality, reliability, trustworthiness, and origins ([HL7 FHIR Provenance](https://fhir.hl7.org/fhir/provenance.html)).

For Track F, these patterns are relevant because WellBe's graph edges are source-linked and evidence-weighted. External provenance standards show common concepts for origin, derivation, agent/activity, and source references, but they do not determine whether the graph response should inline full provenance records, include compact provenance summaries, or link to source/evidence resources.

### 8. API contract versioning and compatibility discipline

OpenAPI describes a language-agnostic interface for HTTP APIs that allows humans and tools to discover service capabilities without implementation access, and OpenAPI documents include both the OpenAPI Specification version and API description metadata such as `info.version` ([OpenAPI Specification 3.1.1](https://swagger.io/specification/)). Microsoft REST API design guidance emphasizes design-first contracts, consistent API styles, and OpenAPI definitions to support parallel work, review, testing, and SDK generation ([Microsoft REST API Design Guidance](https://microsoft.github.io/code-with-engineering-playbook/design/design-patterns/rest-api-design-guidance/)). Google AIP-180 treats APIs as contracts and distinguishes source, wire, and semantic compatibility; it says new required fields should not be added to existing messages and that adding pagination later can be breaking ([Google AIP-180: Backwards Compatibility](https://google.aip.dev/180)). Google AIP-185 places the major API version in the REST path and uses separate stable, beta, and alpha channels for compatibility expectations ([Google AIP-185: API Versioning](https://google.aip.dev/185)). Azure's versioning guidance states that behavior changes require a new API version and describes diff-checking REST definitions for breaking changes ([Azure approach to versioning and avoiding breaking changes](https://devblogs.microsoft.com/azure-sdk/azure-approach-to-versioning-and-avoiding-breaking-changes/)). RFC 9457 defines Problem Details for HTTP APIs as a machine-readable error format ([RFC 9457: Problem Details for HTTP APIs](https://www.rfc-editor.org/rfc/rfc9457.html)).

For Track F, these patterns are relevant to C13 contract evolution: endpoint versioning, payload schema versioning, OpenAPI schema discipline, compatibility checks, and structured error handling for invalid filters, over-limit requests, authorization failures, and unsupported graph-payload versions.

### 9. Authorization, object-level scoping, property-level minimization, and data-layer enforcement

OWASP API Security identifies broken object-level authorization as a common API risk when clients can manipulate object identifiers in paths, query strings, headers, or payloads; OWASP states that every endpoint receiving an object ID and acting on an object should perform object-level authorization checks ([OWASP API1:2023 Broken Object Level Authorization](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/)). OWASP also identifies broken object property-level authorization and advises response property minimization, avoiding generic serialization methods, and schema-based response validation ([OWASP API3:2023 Broken Object Property Level Authorization](https://owasp.org/API-Security/editions/2023/en/0xa3-broken-object-property-level-authorization/)). PostgreSQL row-level security restricts which rows are visible or modifiable per user, evaluates policies before user query conditions, and defaults to deny when row-level security is enabled with no applicable policy ([PostgreSQL Row Security Policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html); [PostgreSQL CREATE POLICY](https://www.postgresql.org/docs/current/sql-createpolicy.html)). Neo4j fine-grained access control separates privileges such as `TRAVERSE`, `READ`, and `MATCH`, and documents subgraph access control through custom roles and privileges ([Neo4j fine-grained access control tutorial](https://www.neo4j.com/docs/operations-manual/current/tutorial/access-control/); [Neo4j read privileges](https://www.neo4j.com/docs/operations-manual/current/authentication-authorization/privileges-reads/)). GraphQL's authorization guidance says authenticated identity is not enough; servers must still determine whether the user may view each piece of data, and authorization logic should live in business logic rather than being duplicated in resolvers ([GraphQL Authorization](https://graphql.org/learn/authorization/)). Google AIP-211 states that authorization should be checked before request validation and cautions against error messages that reveal the existence of inaccessible resources ([Google AIP-211: Authorization Checks](https://google.aip.dev/211)).

For Track F, these patterns are directly relevant to viz scoping. A graph read endpoint that accepts a `threadId`, seed node IDs, edge filters, or traversal depth still requires server-side object authorization, property-level response allowlisting, and query/data-layer scoping so that traversal cannot cross into unscoped user or thread data.

## Decision-neutral findings

### Decision question 1: Query shape for selecting a thread-scoped subgraph

**Established option space.** External patterns divide into two broad families. One family exposes a graph query language over HTTP, as seen with Neo4j's Cypher Query API and Neptune's openCypher HTTP endpoint ([Neo4j Query API](https://www.neo4j.com/docs/query-api/current/); [Amazon Neptune openCypher HTTPS endpoint](https://docs.aws.amazon.com/neptune/latest/userguide/access-graph-opencypher-queries.html)). Another family exposes typed list/query operations with explicit pagination and filtering fields, as in Google AIP-158 and AIP-160 ([Google AIP-158: Pagination](https://google.aip.dev/158); [Google AIP-160: Filtering](https://google.aip.dev/160)). Gremlin/TinkerPop is another traversal-language pattern, but the Gremlin reference notes provider-specific capabilities and limitations, which matters if C13 attempts to hide or normalize C6 provider behavior ([Apache TinkerPop Gremlin Reference](https://tinkerpop.apache.org/docs/current/reference/)).

**Traversal bounds.** Graph traversal can be expressed as bounded path expansion, for example through Cypher quantified path patterns and variable-length relationships ([Neo4j Cypher variable-length paths](https://neo4j.com/docs/cypher-manual/current/patterns/variable-length-paths/)). API security sources outside graph databases treat nested relationship traversal as a resource-control problem: GraphQL security guidance, GraphQL.js complexity controls, and the OWASP GraphQL Cheat Sheet all identify depth limits, pagination, amount limits, timeouts, and complexity/cost analysis as controls for deeply nested or cyclic requests ([GraphQL Security](https://graphql.org/learn/security/); [GraphQL.js Operation Complexity Controls](https://www.graphql-js.org/docs/operation-complexity-controls/); [OWASP GraphQL Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/GraphQL_Cheat_Sheet.html)). For a thread-scoped graph read, the external evidence supports examining explicit maximum depth, maximum nodes, maximum edges, maximum page size, allowed edge types, allowed node types, and server-side cost limits as contract-visible or contract-enforced controls.

**Filters.** AIP-160 treats filters as an API surface that evolves often and uses a single structured `filter` string for expressive filtering, including comparisons, logical operators, and related-object traversal/functions ([Google AIP-160: Filtering](https://google.aip.dev/160)). GraphQL and Relay use schema-defined arguments on connections and fields, and their edge layer can carry edge-specific metadata such as cursors and relationship attributes ([GraphQL Pagination](https://graphql.org/learn/pagination/); [Relay Cursor Connections Specification](https://relay.dev/graphql/connections.htm)). For Track F, these sources map to choices such as typed filter fields, an evolvable structured filter string, or connection-like arguments. The evidence does not establish one canonical graph REST query shape.

**Pagination.** AIP-158 says pagination should not be added after the fact when it may be needed because doing so can be backward-incompatible; it also defines page tokens that require all other request parameters to remain the same across page requests ([Google AIP-158: Pagination](https://google.aip.dev/158)). GraphQL's connection pattern and Relay's specification define cursors at the edge layer plus `pageInfo` for additional-page discovery ([GraphQL Pagination](https://graphql.org/learn/pagination/); [Relay Cursor Connections Specification](https://relay.dev/graphql/connections.htm)). For a graph visualization payload, the unresolved graph-specific question is the pagination unit: nodes, edges, paths, adjacency frontiers, or complete subgraph chunks. External sources provide cursor/page-token patterns but not a single graph visualization pagination unit.

**Scope as part of query semantics.** OWASP API1 warns that API object identifiers can be tampered with in paths, query strings, headers, and payloads, and says every endpoint acting on an object ID should perform object-level authorization checks ([OWASP API1:2023 Broken Object Level Authorization](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/)). For Track F, that maps to C13 treating `threadId`, seed node IDs, edge IDs, provenance IDs, and pagination tokens as authorization-sensitive inputs. A graph query that starts from an authorized thread can still leak data if traversal is not constrained by the authenticated user and thread scope at C13 and C6.

### Decision question 2: Response contract and versioning for C13 visualization clients

**Visualization payload shapes.** Cytoscape.js natively consumes element JSON with node and edge `data` objects, mandatory node IDs, and edge `source`/`target` references; it can accept either a flat list of elements or separate `nodes` and `edges` arrays, and its JSON import/export API uses the same format as initialization ([Cytoscape.js JSON format](https://js.cytoscape.org/)). Sigma's current model uses Graphology as its underlying graph structure, and Graphology serialization uses nodes with `key` and optional `attributes`, and edges with `source`, `target`, optional `attributes`, and optional edge `key` ([Sigma.js graph data](https://www.sigmajs.org/docs/advanced/data/); [Graphology serialization](https://graphology.github.io/serialization.html)). JSON Graph Format provides a neutral graph serialization with graph, node, and edge metadata fields plus schema validation ([JSON Graph Format](https://jsongraphformat.info/); [JSON Graph Format specification](https://github.com/jsongraph/json-graph-specification/blob/master/README.md)). These sources define an option space: Cytoscape-native JSON, Graphology/Sigma-native serialization, or a canonical graph JSON shape with adapters.

**Metadata and evidence travel.** Cytoscape permits application data inside JSON-serializable element `data`; Graphology permits node and edge `attributes`; JGF permits metadata on graph, node, and edge objects ([Cytoscape.js JSON format](https://js.cytoscape.org/); [Graphology serialization](https://graphology.github.io/serialization.html); [JSON Graph Format specification](https://github.com/jsongraph/json-graph-specification/blob/master/README.md)). W3C PROV and HL7 FHIR Provenance provide external provenance concepts for entities, activities, derivations, agents, targets, and source/origin information ([W3C PROV-DM](https://www.w3.org/TR/prov-dm/); [W3C PROV-JSON](https://www.w3.org/submissions/prov-json/); [HL7 FHIR Provenance](https://fhir.hl7.org/fhir/provenance.html)). For Track F, those sources support the factual finding that provenance and evidence-weight fields can be carried in node/edge metadata or attributes, while fuller provenance records can be represented as linked or embedded structured JSON. The decision space remains whether C13 returns compact visualization metadata, full provenance objects, or source/evidence references that a client can dereference through another scoped endpoint.

**Causal and non-diagnostic edge semantics.** The product context fixes `may_explain` as the strongest causal edge type exposed by the WellBe graph. In response-contract terms, the external evidence only addresses how edge types and metadata can travel; it does not define WellBe's semantic vocabulary. Cytoscape edge data, Graphology edge attributes, and JGF edge relation/metadata fields are all structurally capable of carrying a constrained edge type value such as `may_explain` without changing the underlying C6 schema ([Cytoscape.js JSON format](https://js.cytoscape.org/); [Graphology serialization](https://graphology.github.io/serialization.html); [JSON Graph Format specification](https://github.com/jsongraph/json-graph-specification/blob/master/README.md)).

**Versioning and compatibility.** C13 already uses REST/OpenAPI patterns, and OpenAPI is designed to describe HTTP APIs in a language-agnostic way for humans and tools ([OpenAPI Specification 3.1.1](https://swagger.io/specification/)). AIP-180 treats APIs as contracts and warns that existing clients should not be broken by minor or patch changes; it specifically calls out adding required fields as incompatible and adding pagination later as potentially breaking ([Google AIP-180: Backwards Compatibility](https://google.aip.dev/180)). AIP-185 uses major versions in REST paths and describes alpha, beta, and stable channels ([Google AIP-185: API Versioning](https://google.aip.dev/185)). Azure's API guidance uses explicit `api-version` values and contract diff checks to control breaking changes ([Azure approach to versioning and avoiding breaking changes](https://devblogs.microsoft.com/azure-sdk/azure-approach-to-versioning-and-avoiding-breaking-changes/)). These sources map to C13 choices such as endpoint major versioning, query-parameter versioning, media-type versioning, payload `schemaVersion`, OpenAPI diff checks, and compatibility rules for additive versus breaking graph-payload changes.

**Errors and limits.** RFC 9457 defines a standard machine-readable Problem Details format for HTTP API errors ([RFC 9457: Problem Details for HTTP APIs](https://www.rfc-editor.org/rfc/rfc9457.html)). For Track F, this is relevant to errors such as unsupported filter syntax, unsupported graph-payload version, page token mismatch, depth or node/edge limit exceeded, invalid seed node, inaccessible thread, and authorization failure. AIP-211's guidance on authorization before validation and non-leaking error messages is relevant when an error could reveal that an out-of-scope thread, node, or edge exists ([Google AIP-211: Authorization Checks](https://google.aip.dev/211)).

### Decision question 3: Viz scoping and prevention of unscoped data exposure

**Server-side authorization is required for object IDs and properties.** OWASP API1 states that APIs are vulnerable when object identifiers can be manipulated and object-level authorization is missing ([OWASP API1:2023 Broken Object Level Authorization](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/)). OWASP API3 states that APIs should ensure the user is allowed to access each exposed property, avoid generic serialization methods, cherry-pick returned properties, and validate responses with schemas ([OWASP API3:2023 Broken Object Property Level Authorization](https://owasp.org/API-Security/editions/2023/en/0xa3-broken-object-property-level-authorization/)). For Track F, this maps to both topology scoping and attribute scoping: even if a node or edge is allowed in a thread view, its properties, labels, provenance details, or source snippets may need independent allowlisting.

**Data-layer scoping patterns.** PostgreSQL row-level security provides a data-layer pattern where visibility policies are evaluated per row before user query conditions, and no applicable policy under enabled RLS results in default deny ([PostgreSQL Row Security Policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html); [PostgreSQL CREATE POLICY](https://www.postgresql.org/docs/current/sql-createpolicy.html)). Neo4j's privilege model separates finding graph topology from reading properties through privileges such as `TRAVERSE`, `READ`, and `MATCH`, and its fine-grained access control documentation describes custom roles for subgraph access ([Neo4j read privileges](https://www.neo4j.com/docs/operations-manual/current/authentication-authorization/privileges-reads/); [Neo4j fine-grained access control tutorial](https://www.neo4j.com/docs/operations-manual/current/tutorial/access-control/)). These sources establish a pattern of enforcing visibility below the application serializer. They do not determine whether WellBe's C6 store should use database-native policies, query predicates, application-side guards, or a combination.

**Authorization logic placement.** GraphQL authorization guidance says authentication alone is not enough and that authorization logic should be delegated to business logic rather than duplicated in each resolver ([GraphQL Authorization](https://graphql.org/learn/authorization/)). In Track F terms, C13 can authenticate the caller, but the graph-read operation still needs an authorization decision that combines authenticated user, thread ownership or grant, node/edge membership, allowed properties, allowed edge types, provenance visibility, and pagination token integrity. AIP-211's caution about authorization before validation and avoiding existence leaks applies to inaccessible thread IDs, seed node IDs, and source/evidence IDs ([Google AIP-211: Authorization Checks](https://google.aip.dev/211)).

**Over-fetch and traversal leakage controls.** GraphQL security sources describe depth limiting, breadth limiting, pagination, query complexity analysis, and rate limits as protections for nested relationship data ([GraphQL Security](https://graphql.org/learn/security/); [GraphQL.js Operation Complexity Controls](https://www.graphql-js.org/docs/operation-complexity-controls/); [OWASP GraphQL Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/GraphQL_Cheat_Sheet.html)). For a thread graph view, analogous controls include maximum depth, maximum returned nodes and edges, page size ceilings, allowed filters, allowed seed scopes, traversal timeouts, and complexity scoring. These controls address both performance risk and privacy risk because an over-broad traversal can expose unscoped topology.

**Render subset choices.** The external sources do not define what a WellBe thread view should render. They do, however, show structural options for returning a scoped graph: a complete node-link subgraph for an authorized thread; a k-hop expansion from authorized seed nodes; a paginated set of edges or connections; a frontier-based traversal response; or a visualization-shaped graph with some relationships collapsed into counts or summaries. Because WellBe requires strict per-thread and per-user scoping, any render subset that mentions adjacent out-of-thread nodes introduces an existence-disclosure question unless those nodes are explicitly authorized or structurally redacted. OWASP's object-level and property-level guidance, plus AIP-211's non-leaking error guidance, are the relevant external constraints for that choice ([OWASP API1:2023 Broken Object Level Authorization](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/); [OWASP API3:2023 Broken Object Property Level Authorization](https://owasp.org/API-Security/editions/2023/en/0xa3-broken-object-property-level-authorization/); [Google AIP-211: Authorization Checks](https://google.aip.dev/211)).

## Tradeoffs and open questions

### 1. Typed REST query object vs constrained graph query language vs GraphQL-style schema

A typed REST query object can make allowed fields, filters, limits, and response schema explicit in OpenAPI, aligning with design-first REST guidance and compatibility checks ([OpenAPI Specification 3.1.1](https://swagger.io/specification/); [Microsoft REST API Design Guidance](https://microsoft.github.io/code-with-engineering-playbook/design/design-patterns/rest-api-design-guidance/)). A graph query language endpoint can provide expressive traversal power similar to Neo4j Query API or Neptune openCypher HTTP ([Neo4j Query API](https://www.neo4j.com/docs/query-api/current/); [Amazon Neptune openCypher HTTPS endpoint](https://docs.aws.amazon.com/neptune/latest/userguide/access-graph-opencypher-queries.html)). A GraphQL-style schema can expose relationship traversal with connections and field-level typing ([GraphQL Pagination](https://graphql.org/learn/pagination/); [Relay Cursor Connections Specification](https://relay.dev/graphql/connections.htm)). The unresolved tradeoff is flexibility versus enforceability: more expressive query surfaces can require stronger parsing, allowlisting, cost controls, and authorization checks to prevent out-of-scope traversal.

### 2. Pagination unit for graph payloads

External pagination sources define cursor or page-token mechanics, but not the graph-specific unit of pagination ([Google AIP-158: Pagination](https://google.aip.dev/158); [GraphQL Pagination](https://graphql.org/learn/pagination/); [Relay Cursor Connections Specification](https://relay.dev/graphql/connections.htm)). Open choices include paginating nodes, edges, paths, adjacency frontier expansions, or whole subgraph chunks. Paginating nodes can omit edges needed for a coherent view; paginating edges can create orphan or incomplete node sets; paginating paths or frontiers can fit traversal but may be harder for a visualization client to merge; returning whole subgraphs is simpler for rendering but can hit size, cost, and privacy limits.

### 3. Filter representation and evolvability

AIP-160's structured filter string supports evolution and expressive predicates, while typed fields such as `edgeTypes`, `nodeTypes`, `maxDepth`, and `seedNodeIds` are easier for OpenAPI clients to discover and validate ([Google AIP-160: Filtering](https://google.aip.dev/160); [OpenAPI Specification 3.1.1](https://swagger.io/specification/)). The open question is how much filter expressiveness should be exposed to a visualization client. Rich filters can reduce over-fetching, but they can also create more combinations to authorize, test, version, and constrain.

### 4. Response shape: Cytoscape-native, Graphology-native, or neutral canonical graph JSON

Cytoscape-native JSON reduces adaptation for the planned thread view and uses `data.id`, `data.source`, and `data.target` ([Cytoscape.js JSON format](https://js.cytoscape.org/)). Graphology-native serialization aligns with Sigma's underlying model and uses `key` plus `attributes` ([Sigma.js graph data](https://www.sigmajs.org/docs/advanced/data/); [Graphology serialization](https://graphology.github.io/serialization.html)). JGF offers a neutral metadata-bearing graph JSON with schema validation ([JSON Graph Format](https://jsongraphformat.info/); [JSON Graph Format specification](https://github.com/jsongraph/json-graph-specification/blob/master/README.md)). The unresolved tradeoff is client convenience versus long-term contract neutrality: a viz-native response may couple C13 to one client library, while a neutral response may require adapters and client-side transformation.

### 5. Provenance granularity in the visualization response

Cytoscape, Graphology, and JGF all provide places to carry metadata or attributes on nodes and edges ([Cytoscape.js JSON format](https://js.cytoscape.org/); [Graphology serialization](https://graphology.github.io/serialization.html); [JSON Graph Format specification](https://github.com/jsongraph/json-graph-specification/blob/master/README.md)). W3C PROV and FHIR Provenance show richer models for origin, derivation, agents, activities, and targets ([W3C PROV-DM](https://www.w3.org/TR/prov-dm/); [W3C PROV-JSON](https://www.w3.org/submissions/prov-json/); [HL7 FHIR Provenance](https://fhir.hl7.org/fhir/provenance.html)). Open choices include compact evidence summaries on edges, source/evidence identifiers with separate fetches, or embedded provenance records. More embedded provenance can preserve context for the visualization but increases payload size and property-level privacy surface.

### 6. Structural exclusion, redaction, or summaries for out-of-scope adjacent data

OWASP object-level authorization guidance treats object ID access as authorization-sensitive, and property-level guidance warns against over-exposing fields ([OWASP API1:2023 Broken Object Level Authorization](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/); [OWASP API3:2023 Broken Object Property Level Authorization](https://owasp.org/API-Security/editions/2023/en/0xa3-broken-object-property-level-authorization/)). AIP-211 also warns that errors can reveal inaccessible resource existence ([Google AIP-211: Authorization Checks](https://google.aip.dev/211)). The open product/API question is whether adjacent but out-of-thread graph facts should be entirely omitted, represented only as aggregate counts, represented as redacted stubs, or made available only through explicit user grant and scope expansion. Omission minimizes existence leakage; summaries can improve orientation but may still disclose that hidden data exists; redacted stubs can complicate UI and error semantics.

### 7. Where scoping is enforced

PostgreSQL RLS demonstrates data-layer row visibility policies with default-deny behavior, and Neo4j demonstrates graph-specific privileges for traversal and property reading ([PostgreSQL Row Security Policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html); [PostgreSQL CREATE POLICY](https://www.postgresql.org/docs/current/sql-createpolicy.html); [Neo4j read privileges](https://www.neo4j.com/docs/operations-manual/current/authentication-authorization/privileges-reads/)). GraphQL authorization guidance places authorization in business logic rather than duplicated per resolver ([GraphQL Authorization](https://graphql.org/learn/authorization/)). The open architecture question is whether C13, C6 query construction, database-native policy, post-query validation, or several layers together enforce thread scoping. Single-layer enforcement is simpler to reason about operationally but can become a single point of failure; layered enforcement can reduce leakage risk but increases complexity and test burden.

### 8. Versioning mechanism and graph-payload schema evolution

AIP-185 uses major versioning in the REST path, Azure commonly uses an explicit `api-version`, and OpenAPI separates OpenAPI spec version from the API description's own version metadata ([Google AIP-185: API Versioning](https://google.aip.dev/185); [Azure approach to versioning and avoiding breaking changes](https://devblogs.microsoft.com/azure-sdk/azure-approach-to-versioning-and-avoiding-breaking-changes/); [OpenAPI Specification 3.1.1](https://swagger.io/specification/)). AIP-180 warns against adding required fields and highlights semantic compatibility, not only wire compatibility ([Google AIP-180: Backwards Compatibility](https://google.aip.dev/180)). Open questions include whether to version the endpoint path, query parameter, media type, payload `schemaVersion`, OpenAPI document, or a combination; which payload changes are considered additive; how enum expansion is handled by visualization clients; and whether preview graph payload versions can coexist with stable ones.

### 9. Error semantics for inaccessible or invalid graph requests

RFC 9457 provides a standard problem-details envelope for HTTP errors, while AIP-211 emphasizes authorization checks before validation and cautions against revealing inaccessible resource existence ([RFC 9457: Problem Details for HTTP APIs](https://www.rfc-editor.org/rfc/rfc9457.html); [Google AIP-211: Authorization Checks](https://google.aip.dev/211)). The open question is how C13 distinguishes invalid input from unauthorized or nonexistent thread/node IDs without leaking out-of-scope graph facts. Returning a detailed validation error can help client debugging; returning a generic not-found or permission-denied error can reduce existence leakage but may make debugging and support harder.

### 10. Operational limits and partial graph rendering

GraphQL security and OWASP GraphQL guidance describe depth limits, amount limits, timeouts, pagination, and cost analysis as protections for nested relationship reads ([GraphQL Security](https://graphql.org/learn/security/); [GraphQL.js Operation Complexity Controls](https://www.graphql-js.org/docs/operation-complexity-controls/); [OWASP GraphQL Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/GraphQL_Cheat_Sheet.html)). For Track F, maintainers still need to decide how limit enforcement is represented in the success payload: full result only, partial result with truncation metadata, page-token continuation, or error on over-limit request. Partial graph responses can keep the UI responsive but require the client to distinguish missing-because-unloaded from missing-because-unauthorized and missing-because-not-in-thread.

## Approaches considered

Grounded only in the recorded research:

- **Query shape.** Two families: graph-query-language-over-HTTP (Neo4j Query API, Neptune openCypher, Gremlin — expressive but provider-variable and hard to allowlist) vs. typed list/query operations with explicit pagination/filtering (Google AIP-158/160). GraphQL connections (Relay) are a third. Pagination should be in the contract from the start (AIP-158); the graph-specific *unit* (nodes/edges/paths/frontier/subgraph) is undefined by the sources.
- **Response/versioning.** Viz-native shapes (Cytoscape element JSON, Graphology/Sigma serialization) vs. neutral canonical graph JSON (JSON Graph Format) with adapters. All carry node/edge metadata that can hold provenance + a constrained edge type (`may_explain`). W3C PROV / FHIR Provenance can travel inline or by reference. Versioning discipline: AIP-180 (additive vs. breaking), AIP-185 (major version in path), Azure `api-version`, OpenAPI; errors via RFC 9457 Problem Details.
- **Scoping.** OWASP API1 (broken object-level authz) and API3 (property-level authz) require server-side object + property checks; PostgreSQL RLS and Neo4j `TRAVERSE`/`READ`/`MATCH` show data-layer enforcement; GraphQL authz guidance places authz in business logic; AIP-211 says authorize before validation and don't leak existence of inaccessible resources.

## Decision

1. **Query shape = a typed REST/OpenAPI graph-read operation** scoped to a single authorized `threadId` — not raw Cypher/Gremlin passthrough and not GraphQL. Bounded traversal is contract-visible and server-enforced: `maxDepth`, typed `nodeTypes`/`edgeTypes` allowlists, `maxNodes`/`maxEdges`, cost limit, and timeout. `threadId` and seed node ids are authorization-sensitive inputs validated server-side. **Pagination ships in v1** (cursor/`nextPageToken`, AIP-158 style); the pagination unit is the **subgraph chunk** (nodes + incident edges) plus `pageInfo`, to keep the visualization renderable.
2. **Response = neutral canonical node-link JSON** (`nodes[]` with id/type/attributes, `edges[]` with source/target/`relation`/attributes/metadata) carrying a `schemaVersion`, adapted client-side to Cytoscape/Sigma — C13 is **not** coupled to one viz library. Edge `relation` uses the constrained vocabulary including `may_explain` (the ceiling). Provenance/evidence travels as **compact summaries** on node/edge metadata (source type, evidence weight, source-ref id); full provenance is fetched from a **separate scoped endpoint**, not inlined. Errors use RFC 9457. Versioning: major version in path + payload `schemaVersion`, additive-only within a major, OpenAPI backwards-compat diff in CI.
3. **Viz scoping = defense in depth.** Object-level authorization on threadId/seed/node/edge ids (API1); property-level allowlisting of returned attributes incl. provenance fields (API3); data-layer scoping via query predicates anchored to the authenticated user + thread; authorization-before-validation with non-leaking errors (AIP-211). **Out-of-thread adjacent nodes are structurally omitted** (not summarized, not stubbed) so their existence is never disclosed. The depth/node/edge/timeout limits double as over-fetch/leakage controls.

## Trade-offs accepted

- **Typed REST over an expressive query language:** less client flexibility, but enforceable allowlists, property minimization, versionability, and privacy safety — decisive for a per-user/per-thread personal graph.
- **Neutral canonical payload over viz-native:** requires a small client adapter, but avoids library lock-in and keeps property allowlisting server-side.
- **Subgraph-chunk pagination:** simpler for rendering (may refetch) over edge/path pagination which can orphan nodes.
- **Omit out-of-thread adjacency entirely:** less surrounding "context" in the view, but zero existence leakage.

## Implementation notes

- **C13:** typed graph-read op + OpenAPI schema + RFC 9457 errors; CI runs an OpenAPI backwards-compat diff and authz tests for object/property/traversal scoping.
- **C6:** enforce user+thread-anchored predicates at the data layer; emit canonical node-link with compact provenance + constrained edge-type vocabulary; expose a separate scoped provenance-detail endpoint.
- **Deferred (tracked):** exact default limits (depth/nodes/edges/page size) and cursor encoding — to implementation.
